### Prototype

**You own the design decision, not the code. The prototype is a throwaway instrument. The real build follows Feature.**

The one playbook where the Laziness Protocol's "smallest change" and the verification bar invert. Speed over polish, code quality does not matter, no planning. The rigor is in picking the right design cheaply. Propose variations the user didn't ask for, throw an approach away and try another.

Prototype runs on request, on an empirical fork, and by default before Feature builds a new or reworked screen. A screen that already has a picked art board or a locked design reference skips it.

1. Scope the decision the prototype exists to make: which layout, which interaction, which density, or for an empirical fork which behavior, timing, or approach. No decision means no prototype. Route to Feature.
2. For a screen, write the contract before any variant. The contract names the types the screen reads, the API shape that serves them, and every state the screen can be in (at least loading, empty, error, and full), plus one shared sample-data file that fills each state. Take it from `architect`'s output when one exists. Every variant renders from this one contract and this one sample data, so variants differ in layout and feel and never in what the backend has to supply.
3. Gather references when the design space is open. Search for prior art, summarize a moodboard of themes, palettes, and layouts, let the user pick directions before building. Skip when the direction is set.
4. Build throwaway in an isolated scratch dir, separate from production source. For a visual decision, vanilla HTML/CSS/JS or the lightest stack that renders the idea, CDN deps, a dev server with hot reload. For a behavioral or timing decision, the smallest script that exercises the question. No production framework, no tests, no abstractions.
5. When comparing alternatives, build three or four, each labeled with a letter. This is the **exhaust-the-design-space** principle skill made cheap. For a screen, show every variant in every contract state, at desktop and phone width. Make the variants genuinely different in layout, tone and how much product they show, and treat every comment the user already left on the screen as a constraint on all of them. Before the user sees any variant, have a separate reviewer agent, on a different model from the one that built them, judge each against those constraints, the contract, and how distinct it is from the others. Fix or drop the weak ones, and keep each survivor's verdict in a line or two.
6. Put the variants where the user can review them. When the session has the Artifact tool, publish them as one art board and watch it for comments, as [the art board reference](../references/art-board.md) says, so the user can review and comment from a phone. Otherwise build them behind one switcher (buttons or a keypress).
7. Verify on the matching surface. For a visual decision, screenshot each variant via the driver skill and drive the interaction. For a behavioral or timing decision, observe the thing you are deciding by logging the timing, printing the output, or watching the render. The observation is the test here, not an assertion.
8. Present alternatives, tradeoffs, and a recommendation. On an art board, the user's comments sent to Claude are the pick: merge the pieces they name into one more board, the way `arena` grafts, and reply in each comment thread.
9. Check the pick against the contract. List every field, action, and state the picked design shows, and match each one to the contract. When something has no match, update the contract first and say so before any build starts. A picked design never quietly needs data the plan lacks.
10. Record the pick where the work is tracked: screenshots of the picked design and the art board link on the issue or plan. The output is the decision plus the throwaway artifact, not shippable code. Hand the chosen direction and the contract to **Feature** (or `architect` for the shape) for the real build.

**Reply:** the variants explored, the evidence (the art board link or screenshots for a visual decision, the observed output or timing for a behavioral one), tradeoffs, your recommendation or the merged pick, any contract change, and the scratch path. Say plainly that the prototype is throwaway.
